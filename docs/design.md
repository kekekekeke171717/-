# 设计说明 · 门诊预约与分诊协作助手（MVP）

> 这份文档回答三个问题：**为什么做成这样**、**放弃了什么**、**怎么验证它没跑偏**。
> 所有设计决定的出处都能追溯到 Discovery Lab 的访谈事实编号（f00–f55）。

---

## 0. 一句话定位

**它不是分诊系统，是"次序解释引擎"。**

门诊真正卡住的地方不是医生不会看病，而是三件事没人说清楚：

1. 谁排在我前面，为什么？（事实 f10：迟到患者与现场加号混在队列里，护士反复解释次序）
2. 我还要等多久？（事实 f50：三种口径的"等待"各说各话）
3. 我前面的医生去哪了？（事实 f11：医生临时处理急诊，排班未同步，患者收到准点到诊通知）

本 MVP 的全部功能，就是让这三句话有统一、可追溯、可复核的答案。

## 1. 目标与非目标

### 目标（明确要做）

| # | 目标 | 验收口径 | 事实依据 |
|---|---|---|---|
| G1 | 给出可解释的候诊次序建议 | 每条建议必带原记录依据 | f15 |
| G2 | 统一患者解释口径 | 解释文案由规则产出，不由护士自由发挥 | f10 / f14 |
| G3 | 让三种等待口径显式并存 | 看板同时显示三个数，不合并 | f50 / f53 |
| G4 | 隔离脏数据 | 有歧义记录不进建议样本 | f33 |
| G5 | 全程可审计 | 能按业务编号重建当时处理链路 | f45 |

### 非目标（明确不做）

| # | 不做的事 | 为什么 |
|---|---|---|
| N1 | 自动分诊 / 诊断 / 医嘱 | 事实 f05：范围就是"时间解释与队列信息辅助"，专业判断由医护确认 |
| N2 | 写回 HIS / 预约平台 / 叫号系统 | 事实 f32：接口权限为只读 |
| N3 | 实时秒级推送 | 事实 f34：试点阶段每天两次授权更新，超时须标注"暂未更新" |
| N4 | 多院区 / 住院 / 医保结算 | 超出首期试点范围（f05 明确两院区门诊先行） |
| N5 | 用节省工时直接推算 ROI | 事实 f03：收益须扣除维护与人工复核成本 |

> N5 值得单独强调。很多方案在这儿"注水"：把"省了护士 X 分钟"直接乘以时薪算成回款。
> 但访谈里运营主任明确要求扣除维护与人工复核成本 —— 因为本方案**必然增加复核工时**，
> 只是把"反复口头解释"的低价值时间换成了"看一眼确认"的高价值时间。

## 2. 架构：四层，单向依赖

```
        展示层  io.render_dashboard()  →  out/dashboard.html（单文件，无外部资源）
          ↑
        编排层  main.py   check / snapshot / demo / serve
          ↑
        业务层  core/queue.py（回放与排序）  core/rules.py（规则）  core/audit.py（审计）
          ↑
        数据层  utils/config.py  utils/io.py  utils/quality.py  core/models.py
```

**单向依赖是刻意的**：业务层不认识 HTML，展示层不做决策。
这样即使将来换成企业微信卡片、护士站大屏，规则代码一行不用改。

### 为什么用"回放"而不是"实时"

首期采用**历史资料回放**（事实 f05 原文："首期采用历史资料回放，再做小范围并行试点，不直接替换现有业务"）。

回放有三个好处：

1. **零风险**：不接生产库，出问题止步于一个 HTML 文件
2. **可对照**：同一批到达过程，用"先到先看"和"建议策略"各跑一遍，差值就是方案价值
3. **可复现**：任何人 clone 下来 `python -m clinic_triage.main demo`，数字完全一致

`simulate(patients, cfg, policy)` 支持两种策略：

- `fifo` —— 现状基线：纯按签到时间先进先出
- `assisted` —— 建议策略：按规则分带排序后，再由人工确认生效

看板左侧的 `中位候诊 68 → 52 分钟` 就是这个对比。**注意措辞**：
这是"同一批数据的策略模拟差值"，不是"上线后必然达成的效果"，代码输出里明确写了这一句。

## 3. 规则引擎：每条规则必须有四样东西

```python
Reason(
    code="LATE_ARRIVAL",          # 机器可读代号，进审计
    label="迟到超过宽限",          # 人可读标签，上看板
    weight=15,                    # 仅用于带内排序，不对外宣称"风险分"
    evidence="预约 09:00，签到 09:26，超时 11 分钟（宽限 15 分钟）",   # 可追溯到原记录
    action="排入本时段末尾，给出新的预计叫号时间；不取消号源",          # 建议动作，非指令
)
```

**没有 `evidence` 的规则不给合并**（CONTRIBUTING R3）。理由来自 f15：
> "建议必须显示对应原记录和待确认字段……错误结果不能覆盖原记录。"

### 六条规则及其事实出处

| code | 规则 | 动作倾向 | 依据 |
|---|---|---|---|
| `EMERGENCY_FLAG` | 急症标记 / 一级分诊 | **强制转人工**，不排序 | f40 / f42 |
| `LATE_ARRIVAL` | 迟到超过宽限 15 分钟 | 让出当前波次 | f10 / f31 |
| `WALK_IN` | 现场加号混入预约队列 | 明确标注来源与预计时段 | f10 |
| `COMEBACK` | 回诊患者（检查后复诊） | 优先复核带 | f01 流程末节点 |
| `VULNERABLE` | 高龄 ≥75 / 低龄 ≤6 / 特殊标记 | 优先复核带 | 常规脆弱人群保护 |
| `DOCTOR_OVERRUN` | 该医生进度落后 >20 分钟 | 更正预计时间（**不承诺具体分钟**） | f11 / f34 |

`weight` 只在同一优先级带内部排序，**不跨带比较**。
这条很重要：如果把"迟到 15"和"急症 100"放同一个分值体系里排序，
就等于在数值上默认了"某种情况下迟到可以压过急症"—— 而 f40 明确禁止这种可能。

### 优先级带（band）

```
EMERGENCY  →  不排序，直接进"急症·转人工"区，等待人工处理
PRIORITY   →  护士确认后可前置（回诊 / 脆弱人群）
NORMAL     →  正常排队
DEFER      →  让出波次（迟到 / 加号），并给出新的预计叫号时段
```

## 4. 数据质量：先体检，再建议

事实 f31 指出三类脏数据：**签到重复、叫号遗漏、等待时间起点不统一**。
事实 f33 进一步明确处理方式：先校验主编号 / 事件时间 / 版本字段，
**有歧义的记录进人工修复队列，不进入自动推荐样本**。

`utils/quality.py` 的 `check()` 产出的问题分为两级：

- `ERROR` —— 阻塞级，记录被打上 `quarantine` 标记，**不参与任何建议计算**
- `WARN`  —— 提示级，记录可用，但在看板上标记"待确认"

`wait_origin_report()` 专门量化"三套口径差多少"：
算出同一批患者按到院 / 签到 / 预约三种起点统计的等待差值，
直接放在看板右侧 —— **把分歧摆到台面上，而不是偷偷选一个。**

## 5. 审计：能重建当时现场

事实 f45 要求：
> "审计时应能重建'预约 → 到院登记 → 分诊 → 候诊 → 接诊 → 检查交接'中的这次处理，
> 不记录账号口令或……"

`core/audit.py` 落 JSONL（每行一条，便于追加与离线分析）：

```json
{"at":"2026-10-29T20:58:11","appt_id":"A0007","action":"suggest",
 "operator":"system","reason_code":"LATE_ARRIVAL","note":"...",
 "snapshot_version":"snapshot-09:20","prev_status":"","status":"PENDING"}
```

关键设计：

- **只记业务编号，不记任何患者身份信息**
- 每条含 `snapshot_version`，回答"你当时看的是哪一版数据"
- `replay_chain(records, appt_id)` 能按号重建完整链路，直接应付质控抽查
- 系统只产出 `PENDING`，**人不点确认，建议就不生效**（f15 / f44）

## 6. 降级与兜底

事实 f35 给出断网处理办法，代码逐条落实：

| 场景 | 行为 |
|---|---|
| 接口中断 | 继续使用带时间戳的上一份只读快照，界面显示"暂未更新" |
| 重连 | 按业务编号去重补齐，**不反复触发同一待办** |
| 快照超时 | 标记"待刷新"，不作为实时承诺 |
| 规则版本冲突 | 附两个版本给质控，**不自行合并，不选较宽松条款**（f24） |
| 涉及最终决定的操作 | 转人工，标注触发原因、接手人、确认时间（f44） |

看板顶部永远显示"数据截止时间" —— 这是刻意设计的视觉锚点：
让护士在回答患者之前先看一眼这个时间，**避免把历史快照当实时承诺**。

## 7. 为什么不做的两个"看起来很美"的功能

### 7.1 不做"预计还需等待 XX 分钟"

技术上不难，但没有做。理由：

- 事实 f34：信息超过一个更新周期就标为待刷新，**不能作为实时承诺**
- 一旦屏幕上出现具体分钟数，它就从"参考"变成了"承诺"，投诉口径立刻变化（f54）

折中方案：给出**预计叫号时段**（如"预计 10:20–10:35 之间叫号"）而非精确分钟，
并在文案里固定带上"依据 XX:XX 的数据"。

### 7.2 不做"智能加号审批"

加号要不要放、放几个，是医疗资源的分配决策，涉及 f41（最终决定须对应审批人确认）。
本 MVP 只**标注**加号患者在队列中的位置和来源，**不对是否加号给任何倾向性建议**。

## 9. 已知局限（诚实清单）

1. `data/appointments.csv` 是**合成数据**，指标的绝对值不具参考意义，
   只有 `fifo` vs `assisted` 的**相对差值**代表规则的作用方向
2. `DOCTOR_OVERRUN` 目前是静态参数注入，未实现真正的进度预测
3. 队列模型是单医生单队列串行，未建模检查返回后再候诊的二次排队
4. 看板是静态 HTML，没有实现"护士点击确认"的写回（符合只读约束，但意味着复核动作需在纸质/原系统完成）
5. 规则权重由业务判断设定，**尚未经过真实数据标定**

> 第 5 条最重要：**不要拿着"中位下降 X%"去汇报**。
> 它证明的是"这套规则在当前假设下会这样排序"，不是"上线就能降 X%"。
