# 门诊预约与分诊协作 · 业务挖掘与需求洞察

> 来源：FDE Discovery Lab（`healthcare-appointments` 场景）
> 采集方式：6 个岗位角色 × 结构化访谈，共取得 **35 条事实**
> 每条事实都带原文、证据编号与验收口径，可逐条追溯到访谈记录（`医疗-00x`）
>
> 这份文档是后续所有设计、报价、验收的**唯一事实依据**。
> 设计文档里的每个决定都标注了事实编号，例如 `f40` = 第 40 条事实。

## 0. 三十秒版本

| 问题 | 现状 | 目标 | 出处 |
|---|---|---|---|
| 候诊多久 | 中位数 **68 分钟** | **40 分钟** | f00 |
| 爽约率 | **19%** | **10%** | f00 |
| 导诊解释负担 | 每日 **180 次**排队咨询（日均 1600 人次） | 显著下降 | f12 / f51 |
| 系统能不能降候诊 | 回放显示平均候诊可降约 **19%** | 试点复测 ≥20% | 本项目 MVP 回放 + f02 |
| 预算 | 首期 **16 万元** | 含集成、培训、验证 | f03 |
| 上线范围 | 2 个常规门诊，并行试点 4 周 | 不替换现有流程 | f02 / f05 |

一句话概括这个场景的本质矛盾：

> **患者要一个能信的解释，护士给不出；系统有数据，但散在三个互不相通的系统里。**

## 2. 业务流程与节点耗时

访谈给出的主流程（f01 / f20）：

```
预约 → 到院登记 → 分诊 → 候诊 → 接诊 → 检查交接
```

**关键发现：管理层还没有分别量出每个节点的等待和处理时间。**

这意味着一件事：**现在不能承诺"缩短 X 分钟"，因为还没有可对比的基线。**
所以本方案第一阶段必须先做基线测量，再谈优化 —— 这是 MVP 以"回放"形式存在的直接原因。

各岗位的输入输出与责任人（f20 / f21）：

| 节点 | 输入 | 输出 | 待办责任人 |
|---|---|---|---|
| 预约 | 号源、医生排班 | 预约记录 | 排班管理员 |
| 到院登记 | 预约记录、签到 | 到院状态 | 导诊护士 |
| 分诊 | 主诉、生命体征 | 分诊等级 | 护士（专业判断） |
| 候诊 | 分诊结果、队列 | 叫号次序 | 导诊护士 |
| 接诊 | 叫号、病历 | 医嘱/处方 | 医生 |
| 检查交接 | 检查单 | 检查回执、回诊安排 | 排班管理员 |

退回上一节点时必须保留原因，不许只写"已处理"（f20）。

## 4. 从三十五条事实里读出来的六件事

事实本身不说话，要交叉着读才有结论。

### 4.1 三套"等待"口径是最大的隐性冲突（f50 / f53）

同一个患者，同一段等待，三个部门算出三个数：

| 部门 | 起点 | 倾向的结果 |
|---|---|---|
| 患者 | 到院 | 最长 |
| 叫号系统 | 签到 | 居中 |
| 运营 | 预约时间 | 最短 |

这不是数据质量问题，是**立场问题**。所以方案不能"选一个正确的"，
必须三套并存并明示差异（MVP 的 `quality.wait_origin_report()` 就干这个）。
谁要是偷偷合并成一个数，试点验收那天一定吵架。

### 4.2 脏数据必须隔离，而不是修复（f33）

f31 点名三类问题：签到重复、叫号遗漏、等待起点不统一。
f33 给的处理办法很明确 —— **有歧义的记录进人工修复队列，不进自动推荐样本**。

这条直接决定了 MVP 的分层：`quality.check()` 的输出分「阻断」和「提示」两级，
被标阻断的记录不参与任何建议计算。**宁可少给几条建议，也不能给一条查无实据的建议。**

### 4.3 让位必须有上限（f10 + 工程实践）

f10 说的是护士反复解释次序。如果只做"迟到者让出波次"这条规则，
队尾的人会被无限往后推 —— MVP 早期回放里出现过单个患者等待 **200 分钟以上**。

于是有了 `defer_protect_min`（默认 45 分钟）：等待超过阈值就自动回到正常次序，
并且明确告诉患者"已转为正常次序"。**这不是给迟到者的奖励，是把最费口舌的那件事制度化。**

### 4.4 纯排序救不了候诊长度（f30 + 排队论）

这条不在访谈里，是从数据里算出来的，但它决定了整个方案能不能兑现承诺。

在"医生从不空等"的假设下：

```
Σ等待时间 = Σ开始时刻 − Σ到达时刻 = 与排序方式无关的常数
```

纯排序只能把等待从一群人转移给另一群人。真正能压低**总量**的只有减少吞吐损失 ——
也就是 f00 里那个 **19% 的爽约率**造成的叫号空转。

MVP 用三种策略回放验证了这一点：

> 下表每次 `python scripts/gen_data.py` 后会略有浮动，重跑请以 `out/replay.json` 为准。

| 策略 | 中位候诊 | 平均候诊 | 最长候诊 | 叫空号 |
|---|---|---|---|---|
| 现状（按号序叫号） | 47.5 分钟 | 46.9 分钟 | 130 分钟 | 25 次 |
| 建议策略（动态排序） | **19.5 分钟** | **38.4 分钟**（**−18.1%**） | 155 分钟 | 0 次 |
| 参考线（纯按到达先后） | 34.0 分钟 | 39.2 分钟 | 112 分钟 | 0 次 |

建议策略的平均候诊已经贴着参考线（相差 0.8 分钟/人）——
**排序能拿的空间基本到顶了**，还想往下压只能加号源或改排班。
这个结论比"我们能降 40%"有用得多，也比它诚实：

- 中位数降了 **58.9%**（多数人明显少等）；
- 但**最长等待反而变长**（130 → 155 分钟）—— 迟到与加号被有意识地往后放，
  这部分人替大家承担了成本。这个代价要不要接受，是院方的管理决定，
  不是算法能替你拍板的。

### 4.5 权限边界不许含糊（f22 / f32 / f41）

三个角色从三个角度说了同一件事：

- 排班管理员：不能代替质控签核，不能批准范围外的操作（f22）
- 系统工程师：接口只读，不能自动分诊或改医嘱（f32）
- 质控专员：最终决定要对应审批人确认，不能借用他人账号（f41）

翻译成代码就是 CONTRIBUTING 里的 R1/R2：**任何情况下不得写回业务系统，急症一律转人工。**

### 4.6 试点怎么算成功，一开始就写死（f02 / f42 / f53 / f55）

| 项 | 内容 |
|---|---|
| 主指标 | 候诊等待时间下降 20% |
| 安全指标 | 急症识别提示 100% 转人工 |
| 统计纪律 | 固定分母、明确排除规则与统计周期，禁止把同一业务拆成多次"成功" |
| 改进纪律 | 每周收集误判例子，**先复测指标再改规则版本** |
| 停止条件 | 触及任一即暂停试点，负责人复盘 |

注意 f55 那条"先复测再改规则" —— 它是在防止团队为了好看而反复调参。

## 5. 需求优先级（MoSCoW）

| 优先级 | 需求 | 事实依据 |

## 6. 这份文档怎么用

1. **写代码前**：确认这个需求背后有没有事实编号。没有就去问，别猜。

3. **试点验收时**：对照第 4.6 节的表，一条一条核，**不许临时改口径**。
